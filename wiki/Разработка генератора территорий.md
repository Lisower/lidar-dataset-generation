# Разработка генератора территорий

Руководство описывает текущую реализацию `terrains-generator`. Для запуска, каталога пресетов и полного справочника RON см. [Генерация общих территорий](Генерация%20территорий.md).

## Границы ответственности

`terrains-generator` отвечает за состав сцены и размещение объектов. Новые территории должны собираться комбинацией существующих моделей.

| Данные / действие | Владелец |
| --- | --- |
| Рельеф, вода, водопады, их геометрия и облака | `landscapes-generator` |
| Здания и строительные пресеты | `buildings-generator` |
| Деревья, кусты, пальмы, можжевельник, пучки травы | `plants-generator` |
| Каталог, манифесты, seed, классы точек, XYZ-экспорт | `generation-core` |
| Камеры и интерфейс выбора пресетов | `bevy-utils` |
| Выбор моделей, планировка улиц, правила размещения, сборка сцены | `terrains-generator` |

При добавлении территории сначала найдите подходящие `manifest.ron` и `config.ron` в существующем каталоге. Если нужной модели нет, укажите это явно и согласуйте изменение соответствующего генератора. Геометрию дерева, дома или другого объекта внутри `terrains-generator` не дублируйте.

## Карта модулей

Пути приведены относительно корня репозитория.

| Файл | Назначение |
| --- | --- |
| `crates/terrains-generator/src/lib.rs` | Публичные модули и экспорт API |
| `crates/terrains-generator/src/preset.rs` | Встроенные имена, `TerrainPresetData`, настройки размещения и травы, проверка параметров |
| `crates/terrains-generator/src/sources.rs` | `PresetSource`, раскрытие групп, устранение повторных ссылок, взвешенный выбор |
| `crates/terrains-generator/src/placement.rs` | `PlacementMap`, проверки оснований, пространственные индексы, расстояние до воды |
| `crates/terrains-generator/src/scene.rs` | Общая сборка `TerrainScene`, улицы и размещение объектов, объединение облака |
| `crates/terrains-generator/src/viewer.rs` | Интеграция существующих рендереров, панель, смена сцены и режима |
| `crates/terrains-generator/src/main.rs` | CLI, выбор каталогов данных, запуск viewer/headless |
| `crates/terrains-generator/examples/dump_presets.rs` | Запись встроенных настроек в каталог RON |
| `crates/terrains-generator/examples/profile_grass.rs` | Воспроизводимое сравнение генерации травы и подсчёт ресурсов ECS |
| `crates/terrains-generator/tests/territories.rs` | Интеграционные проверки каталога и генерации |
| `crates/plants-generator/src/generation/instances.rs` | Общие `GrassField` и `GrassInstance`, пул вариантов, облако экземпляров |
| `crates/plants-generator/src/visual/mod.rs` | Существующий рендерер растений и `spawn_grass_instances` |
| `crates/generation-core/src/presets/mod.rs` | Общий `PresetStore`; реальный каталог группы хранится в `PresetGroup.dir` |

`src/terrain.rs` — старый файл, не подключённый в `lib.rs`. Рабочая композиция находится в `scene.rs`; изменения только в `terrain.rs` не изменят поведение приложения.

## Последовательность генерации

1. Проверить `TerrainPresetData`, раскрыть источники, загрузить конфиги и проверить типы растений. Валидация конфигурации не заменяет внутренние ограничения каждого нижележащего генератора.
2. Выбрать один базовый ландшафт по весу и seed. Получить его через `landscapes-generator`, привести размер к 100 м и ограничить шум при наличии застройки.
3. Создать `PlacementMap`, рассчитать сеточную дистанцию до воды, резервировать прямоугольные коридоры улиц.
4. Создать здания через `Building::generate`, подобрать места с учётом реальных размеров, установить поворот фасада к улице.
5. Создать деревья и кусты через `Plant::generate`, подобрать места по кластерам, уклонам, воде и свободным областям.
6. Создать ограниченный пул травы через существующий `generate_tuft`, затем размещать лёгкие экземпляры. Вернуть данные `TerrainScene` и измеренное время генерации.

Один объект создаётся до попыток найти ему место; неудачная попытка не должна заново генерировать его геометрию. Если подобрать место не удалось, объект пропускается. Здания получают до 250 попыток, деревья и кусты — до 350, экземпляр травы — до 30.

## Публичный API

| Вызов | Результат и использование |
| --- | --- |
| `generate(preset, seed)` | `TerrainScene` со встроенными настройками территории |
| `generate_from_data(&data, seed, root)` | Совместимая обёртка; при ошибке конфигурации вызывает panic |
| `try_generate_from_data(&data, seed, root)` | `Result<TerrainScene, String>`; использовать для пользовательских файлов, CLI и GUI |
| `TerrainPresetData::from_preset(preset)` | Встроенные настройки без явного корня каталога |
| `TerrainPresetData::from_preset_with(preset, root)` | Встроенные настройки с возможностью ссылаться на группы каталога |
| `TerrainScene::object_count()` | Число деревьев, кустов, экземпляров травы и зданий |
| `TerrainScene::point_cloud()` | Полное облако сцены с преобразованиями и классами точек |
| `GrassField::point_cloud()` | Облако только экземпляров травы |

`root` — `Option<&Path>` на общий каталог `presets/`. Для раскрытия групп он обязателен. Без корня поддерживаются известные встроенные идентификаторы моделей; произвольные файлы нужно загружать с явным корнем.

Пример кода для бинарного крейта workspace, запускаемого из корня репозитория:

```rust
use std::path::Path;
use generation_core::Seed;
use terrains_generator::{TerrainPreset, TerrainPresetData, try_generate_from_data};

fn main() -> Result<(), String> {
    let root = Path::new("presets");
    let data = TerrainPresetData::from_preset_with(
        TerrainPreset::ConiferForest,
        Some(root),
    );
    let scene = try_generate_from_data(&data, Seed::new(42), Some(root))?;
    let cloud = scene.point_cloud();
    generation_core::point_clouds::export::write_xyz(
        &cloud,
        "assets/export/conifer-forest.xyz",
    ).map_err(|error| error.to_string())?;
    Ok(())
}
```

`TerrainScene.grass` содержит `GrassField`, а не прежний вектор `PlacedTuft`. Размещения доступны в `.instances`, геометрия — в `.variants`. API `PlacedTuft` и `PlantScene` самого генератора растений сохранён.

## Координаты и преобразования

Данные генераторов используют горизонтальную плоскость `XY`, вертикаль `Z`, единицы — метры. Карта центрирована в начале координат и имеет стороны от −50 до +50 м. Проверки размещения оставляют запас до границ под радиус объекта и отступ.

| Объект | Данные размещения |
| --- | --- |
| Дерево / куст | `PlacedPlant.position: Vec2`; высота основания запрашивается у `landscape.heightfield` |
| Здание | `PlacedBuilding.position: Vec3`, поворот вокруг Z |
| Трава | `GrassInstance.position: Vec3`, поворот вокруг Z и равномерный масштаб |

Рендереры переводят данные в Bevy с вертикалью `Y`: `(x, y, z)` → `(x, z, -y)`. Не применяйте этот перевод к XYZ-экспорту второй раз. Облака деревьев, зданий и вариантов травы до размещения находятся в локальной системе объекта.

## Занятость и допустимые пересечения

В `PlacementMap` используются два пространственных индекса с ячейкой 4 м:

- `objects` — полные области зданий, коридоров, крон и кустов;
- `ground` — области зданий, коридоров, кустов, оснований стволов и уже размещённой травы.

`try_place` проверяет объёмные объекты и резервирует их в обоих индексах. `try_place_tree` резервирует крону в `objects`, а в `ground` — только основание ствола. Его радиус вычисляется по низким точкам существующего облака растения (`z < 0.5`) с запасом. `try_place_grass` проверяет и изменяет только наземный индекс.

Вода и уклон проверяются независимо от индексов. Уклон оценивается в центре и четырёх точках по радиусу основания; это выборочная проверка, а не точная адаптация фундамента к рельефу. Дистанция до воды — двухпроходное сеточное приближение chamfer по восьми соседям.

`TerrainScene.footprints` содержит области объёмных объектов и коридоров, но не полные размещения травы. Коридоры на перекрёстках могут пересекаться. Не используйте безусловный тест «все footprint попарно не пересекаются» для всей сцены: учитывайте слои и разрешённые пересечения.

## Улицы

`RoadCorridor { start, end, width }` описывает только резервирование места. При `Grid` создаются два пересекающихся коридора, образующие четыре квартала. При `Village` основная улица смещается по seed и имеет ответвление.

Габариты здания берутся из существующей модели и дополнительно учитывают свес крыши. Кандидат выбирается рядом с коридором с запасом под размер и `setback`. Вход существующих строительных моделей направлен по локальной оси `-Y`; поворот вычисляется так, чтобы эта сторона смотрела на улицу. `Cabin` размещает дом вблизи центра без создания коридоров.

## Трава и рендеринг

`GrassField` хранит два массива:

- `variants: Vec<GrassTuft>` — небольшой пул готовой геометрии, полученной из существующего `generate_tuft`;
- `instances: Vec<GrassInstance>` — индекс варианта, координаты, угол и масштаб каждого размещения.

Пул содержит `число видов травы × variants_per_preset` вариантов, когда трава включена. Геометрия не копируется на каждый пучок. `spawn_grass_instances` создаёт визуальные меши и материалы на вариант, а экземпляры используют общие handles. Это позволяет штатному механизму Bevy объединять отрисовку одинаковых мешей и материалов. Сущности экземпляров остаются отдельными: их число растёт вместе с количеством травы.

Облако травы объединяется в один меш точек. `GrassInstance::matrix()` определяет преобразование, используемое в headless-облаке; viewer применяет те же координаты, поворот и масштаб. Классы точек при преобразовании сохраняются. Прежнее округление высоты групп травы до полос по 0,5 м не используется.

Оптимизация решает стоимость повторной генерации геометрии и количество GPU-ресурсов. Она не устраняет стоимость размещения, всех ECS-сущностей, построения общего облака или генерации деревьев другими крейтами.

## Детерминированность

Для повторяемости фиксируйте seed, конфигурацию, версии генераторов и содержимое каталога моделей. Сохранение только seed при изменившемся RON не гарантирует прежней сцены.

Случайность разбита на дочерние потоки по строковым меткам, например `landscape-choice`, `building-model`, `trees`, `grass-variants`, `grass-positions`. Кандидаты после раскрытия групп сортируются по id, чтобы порядок обхода файловой системы не влиял на выбор. Нельзя заменять эти потоки на случайность из системной энтропии внутри генерации.

Сравнивать нужно виды объектов, координаты, повороты, масштабы, рельеф и точки с классами. Поля `generation_time` и `grass_generation_time` зависят от выполнения и не должны участвовать в сравнении сцен на равенство.

## Добавление новой территории

Обычный новый вариант создаётся только через `manifest.ron` и `TerrainPresetData` в `config.ron`. Размещение определяется настройками `placement`, а не неизвестным именем, подменённым на `Field`.

Если территория должна стать встроенной и пересоздаваться `dump_presets`:

1. Добавьте запись в таблицу макроса `terrain_presets!` в `preset.rs`: Rust-вариант, id, русское имя, архетип ландшафта и категорию.
2. Задайте отличия конфигурации в `from_preset_with`, переиспользуя общие стратегии.
3. Запустите `dump_presets`, учитывая, что он перезаписывает встроенные файлы.
4. Проверьте diff: не должно быть несвязанных изменений моделей и существующих пользовательских конфигов.
5. Проверьте обнаружение через `--list` и `Ctrl+S`, затем headless-генерацию и viewer.

Макрос обновляет `ALL`, `name`, `label`, `category` и основное сопоставление `from_name`. Не добавляйте отдельный алгоритм геометрии под каждый новый id.

## Проверки и измерение производительности

Быстрый цикл:

```sh
cargo check -p terrains-generator --all-targets
cargo test -p terrains-generator
cargo run -p terrains-generator -- --list
```

Общие проверки:

```sh
cargo check --workspace
cargo test --workspace --no-fail-fast -j 1
cargo fmt --all -- --check
```

Интеграционные тесты читают каталог относительно `CARGO_MANIFEST_DIR`; запускайте их с доступным `presets/` из checkout. В текущем наборе проверяются все 29 файловых территорий, совместимость старого RON, группы, веса, ошибки, правила размещения, виды растений, повторяемость и ресурсы рендерера. Проверка каждого пресета использует уменьшенные счётчики, поэтому она не заменяет испытание плотной сцены.

CPU/ECS-сценарий:

```sh
cargo run -p terrains-generator --example profile_grass -- 10000
```

Он отдельно измеряет прежние вызовы генератора пучков, пул вариантов с размещениями, подготовку ECS и полную плотную лесную сцену. Печатает фактическое количество мешей, материалов и сущностей. Сравнивайте одинаковый профиль сборки и несколько запусков; `dev` и `release` имеют разные затраты.

Графическую проверку выполняйте отдельно: одинаковые пресет, seed, каталог, режим `V`, размеры окна и ракурс камеры. Этот сценарий не включает счётчик FPS; результат CPU-бенчмарка нельзя выдавать за ускорение кадров. Выполненные ранее замеры и известные ошибки workspace находятся в [отчёте](Отчёт%20terrains-generator.md).
